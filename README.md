# C8 Tech Summit

Event website and (upcoming) admin dashboard for C8 Tech Summit 2026, *Navigating Nigeria's AI Revolution: Jobs, Privacy, & Financial Security*, live online on 15 October 2026 at 4:00 PM WAT.

**Stack:** TanStack Start (React 19, Vite, SSR) · Tailwind CSS v4 · Supabase (Postgres, Auth, Storage) · Docker Compose for local infrastructure.

## Requirements

- Node.js 22.12+ (the Docker image uses Node 24) and npm
- Docker with Docker Compose v2

## Quick start (everything in Docker)

```sh
npm install
npm run setup          # creates .env with fresh local secrets
docker compose up -d --build
```

| Service | URL |
|---|---|
| Website | http://localhost:3000 |
| Supabase API (Kong gateway) | http://localhost:8000 |
| Supabase Studio (database UI) | http://localhost:54323 |
| Mailpit (catches all outgoing email) | http://localhost:54324 |
| PostgreSQL | whatever `POSTGRES_HOST` points at (see below) |

The first start takes a minute while Postgres initialises. Migrations in `supabase/migrations/` are applied automatically by the `migrate` service.

## Database

The app runs on any PostgreSQL 15+ server; Supabase Auth, REST and Storage run in Docker on top of it. Configure it in `.env`:

```sh
POSTGRES_HOST=your-db-host
POSTGRES_PORT=5432
POSTGRES_DB=postgres
POSTGRES_USER=postgres          # must be a superuser (creates the service roles)
POSTGRES_PASSWORD=...
DB_SERVICE_PASSWORD=...         # generated by `npm run setup`; used by the service logins
COMPOSE_PROFILES=               # empty = don't start the local database container
```

On `docker compose up`, the `bootstrap` service creates the roles and schemas the Supabase services need (`anon`, `authenticated`, `service_role`, `authenticator`, `supabase_auth_admin`, `supabase_storage_admin`, schemas `auth` and `storage`; see `docker/db/bootstrap.sql`). It is idempotent, so it also runs safely against an existing database. Then Auth and Storage run their own migrations and `migrate` applies `supabase/migrations/`.

**Local database instead:** the `.env.example` defaults (`COMPOSE_PROFILES=local-db`, `POSTGRES_HOST=db`, `POSTGRES_USER=supabase_admin`) start a throwaway Postgres container, exposed on `localhost:54322`. Use this for development so test data stays out of the real database.

## Development (hot reload)

Run the backend services in Docker and the app on your machine:

```sh
npm run services:up    # Postgres, Auth, REST, Storage, Studio, Mailpit + migrations
npm run dev            # http://localhost:3000
```

Stop the services with `npm run services:down`. With the local database, `docker compose --profile local-db down -v` wipes it and uploaded files.

## Scripts

| Command | What it does |
|---|---|
| `npm run setup` | Create `.env` from `.env.example` with generated secrets (`-- --force` to regenerate) |
| `npm run dev` | Vite dev server with SSR and hot reload |
| `npm run build` / `npm start` | Production build into `.output/`, then run it with Node |
| `npm run services:up` / `services:down` | Start/stop the local Supabase stack |
| `npm run db:migrate` | Apply any new migration files (and reload the API's schema cache) |
| `npm run db:seed` | Load sample content from `supabase/seed.sql` (idempotent) |
| `npm run db:types` | Regenerate `src/integrations/supabase/types.ts` from the local database |
| `npm test` / `npm run lint` | Vitest / ESLint |

## Database migrations

Add SQL files to `supabase/migrations/` named `<timestamp>_<description>.sql` (e.g. `20261010120000_blog_posts.sql`), then run `npm run db:migrate`. Each file runs once, inside a transaction, and is recorded in `supabase_migrations.schema_migrations`, the same table the Supabase CLI uses, so the folder can also be pushed to a hosted Supabase project with `supabase db push`.

`supabase/seed.sql` runs once, the first time migrations are applied to an empty database.

## Environment variables

See [`.env.example`](.env.example) for the full list with comments. The important ones:

- `ANON_KEY` / `VITE_SUPABASE_PUBLISHABLE_KEY` — public key; safe in the browser, limited by Row Level Security.
- `SERVICE_ROLE_KEY` / `SUPABASE_SERVICE_ROLE_KEY` — **server only**, bypasses RLS.
- `VITE_*` values are baked into the browser bundle at build time; rebuild (`docker compose up -d --build`) after changing them.
- `SMTP_*` — outgoing email. Locally this is Mailpit; in production use your provider's SMTP settings.

## Email (Resend)

Every successful registration sends a confirmation email with the event details, an "Add to Google Calendar" button and a calendar invite (`.ics`). The result is stored on the registration row (`confirmation_email_status`: `pending` / `sent` / `failed`, plus the provider message id or error). A failed email never fails the registration.

- **Locally** no key is needed: mail goes to Mailpit, http://localhost:54324.
- **Production:** create an API key at [resend.com](https://resend.com), verify your sending domain, then set:

  ```sh
  RESEND_API_KEY=re_...
  EMAIL_FROM="C8 Tech Summit <hello@your-verified-domain.com>"
  EMAIL_REPLY_TO=C8techsummit@gmail.com
  ```

  Blog sign-in links are also sent by the app through Resend. Supabase Auth's own emails (used later for admin invites) can go through Resend's SMTP: `AUTH_SMTP_HOST=smtp.resend.com`, `AUTH_SMTP_PORT=465`, `AUTH_SMTP_USER=resend`, `AUTH_SMTP_PASS=<API key>`.

The template lives in `src/lib/registration-email.server.ts`; event facts (date, time, theme) come from `src/lib/event.ts`.

## Blog and reader sign-in

- `/blog` lists live posts with category filters and pagination; `/blog/<slug>` shows a post; `/rss.xml` is the feed (titles, excerpts and covers only).
- **Gating is enforced on the server.** Anonymous visitors receive only the first `preview_paragraphs` paragraphs of a gated post (default 3); the rest is never sent to the browser. The database also refuses the `content` column to the public API. Posts with `is_free = true` have no wall.
- **Reader sign-in:** the sign-up wall reuses the registration form. On sign-up the confirmation email includes a "Continue reading" magic link; registered readers can request a sign-in link. Links land on `/auth/confirm`, which sets an httpOnly session cookie (stays signed in on that device).
- **Scheduling:** a post with `status = 'scheduled'` goes live automatically once `published_at` passes.
- Posts are stored as Tiptap JSON (`blog_posts.content`); the admin editor arrives in Phase 6. Until then, sample posts come from `scripts/generate-seed.mjs` → `supabase/seed.sql` (`npm run seed:generate && npm run db:seed`).

## Speakers and sponsors

- `/speakers` lists published speakers with a filter per conversation (`?track=privacy`); featured speakers also appear on the homepage. Cards open an accessible profile with bio and social links. Speakers without a photo get a branded placeholder.
- `/sponsors` groups visible sponsors by tier (Headline → Media Partners). Tiers without a partner show an "Available" card that preselects that tier in the enquiry form (`/sponsors?tier=gold#enquire`). No fake sponsors are seeded.
- **Sponsor enquiries** are validated on the server, rate limited (3 per hour per IP), saved to `sponsor_enquiries` (status `new` / `contacted` / `closed`), emailed to `SPONSOR_ENQUIRY_EMAIL` with reply-to set to the enquirer, and acknowledged to the enquirer.
- Until the admin dashboard (Phase 6), edit speakers and sponsors in Supabase Studio (http://localhost:54323) or via `scripts/generate-seed.mjs`.

## Project layout

```
src/routes/            File-based routes (index composes the homepage; owns metadata)
src/components/site/   Site components (header, footer, homepage sections, registration form + modal)
src/components/blog/   Blog listing, article renderer, sign-up wall
src/components/ui/     shadcn/ui primitives
src/lib/               Shared logic; *.functions.ts are server functions
src/integrations/      Supabase clients (client.server.ts = service role, server only)
supabase/migrations/   SQL migrations
docker/                Local Supabase config (Postgres init, Kong gateway, migration runner)
```

## Deployment

`docker build` produces a self-contained Node server image (see `Dockerfile`); pass `VITE_SUPABASE_URL` and `VITE_SUPABASE_PUBLISHABLE_KEY` as build args and the remaining variables at runtime. For production, use a hosted Supabase project (or a hardened self-hosted one) rather than this local stack.
